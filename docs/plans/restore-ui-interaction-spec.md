## 0. 现状缺陷（已核对源码）

1. 恢复确认文案与事实不符 —— `Conversations.tsx:205-207` 写「之后你可以在聊天界面无缝继续对话」，实际：
   - 恢复是 **仅本次运行有效** 的接管（override 不写 metadata，重启即回到原状）；
   - 当前实现走 `continue_inplace`，**新内容会写回源归档**（对仍被飞书 bot 写的归档会双写）。
2. 无来源标识 —— `ConversationSummary` 只有 `id/title/message_count/last_user_preview/original_user_preview`，用户无法知道「这条是飞书/微信来的，可能还在被外部写」。
3. 无「拷贝一份继续」选项 —— GA TUI 对被占用/快照的源会强制拷贝，Web UI 没有对应能力。
4. 失败只弹「恢复失败 + 原始错误」，未按 `code` 映射可读原因（`session_control_active` / `restore_failed` / `agent_busy` 等）。
5. 恢复成功提示（`LiveChat.tsx:305`）只说「已恢复 N 条可视消息」，未说明「本次运行有效」与「当前指向的归档」。
6. 恢复目标不透明 —— 页面只用 `chatStore.sessionId`，确认框里没显示「将清空/替换的是哪条会话」。

## 1. 目标交互（两条流程）

### 1.1 Restore（借历史到当前会话，临时）
```
idle
 ├─ 无活动会话 → alert「请先到聊天页选择或新建会话」（已有）
 ├─ 有活动会话 → confirm（来源感知 + 3 条后果 + 目标会话名）
 │      ├─ 取消 → idle
 │      └─ 确认 → 请求中（按钮禁用）→
 │            ├─ 成功 → 跳 /chat + 系统气泡（含「本次运行有效」提示）
 │            ├─ 409 session_control_active → alert「该会话正在执行操作，请稍后重试」
 │            ├─ 409 restore_failed → alert「归档无法读取或正被占用，可稍后重试」
 │            └─ 其他 → alert（原始原因）
```

### 1.2 Adopt（导入为一条真正的会话，持久）
```
历史页 / 会话栏 → 「导入为新会话」→ confirm（copy + 绑定语义）
  ├─ 取消 → 原状
  └─ 确认 → 请求中 → 成功跳转到新会话
```
语义：拷贝源归档到新 logid + `rotate_archive`/`bind_archive` 绑定 → 新会话 = 普通会话，重启仍在，源归档只读。

## 2. UI 元素变更

### 2.1 来源徽标
- 列表行 + 详情头部加 `source` 徽标：hub / feishu / wechat / qq / wecom / telegram / discord / cli / unknown。
- 后端 `ConversationSummary` 增 `source` 字段（推断信号：归档用户轮是否带 IM `FILE_HINT` 头、归档归属进程等；见第 4 节）。

### 2.2 恢复确认框（重写）
标题：`恢复「<来源名>」到会话「<目标会话名>」？`
正文（按来源分支）：
```
· 目标会话「<目标会话名>」的当前上下文会被替换（旧运行时关闭）
· 恢复内容仅本次运行有效，重启后回到原状（如需持久，改用「导入为新会话」）
· 会复制该会话的历史继续，源归档保持只读（不写回）
```
（copy 模式下无需「来源仍在写入」的额外警告；来源徽标仍保留用于展示）
```
· 这是飞书会话，来源可能仍在被飞书写入，两边同时写会损坏归档
```
按钮：主「恢复并继续」/ 次「取消」。（copy 为唯一模式，不提供「接管原记录」）

### 2.3 成功提示（重写）
```
已从「<来源>」恢复 <N> 条消息到「<目标>」（本次运行有效）。
```
追加一行弱化提示：`该恢复不会持久化；重启后将回到会话原有记录。`

### 2.4 失败映射（按 code）
| code | 文案 |
|---|---|
| session_control_active | 该会话正在执行互斥操作，请稍后重试 |
| restore_failed | 归档无法读取或正被占用，请稍后重试 |
| agent_busy | 该会话任务正在运行，请先停止后再恢复 |
| session_runtime_stopping | 服务正在关闭，请稍后重试 |
| 其他 | 原始错误 |

## 3. Adopt 入口
- 历史页详情操作栏加「导入为新会话」；会话栏可选加同样入口。
- 确认框：`将「<来源>」复制为一条新会话继续？源归档保持只读。`
- 成功后：跳转到新会话，`toast` 提示「已导入为新会话」。

## 4. 后端契约依赖（最小）
1. `ConversationSummary.source: string`（+ 列表/详情 schema、openapi 再生成）。
2. restore 请求支持 `mode: "copy" | "inplace"`（factory `archive_override` 分支扩展；copy 走 GA `continue_copy`，源只读）。
3. adopt：新路由或复用现有能力 —— copy 到新 logid + `rotate_archive`(或 `bind_archive` on 新会话) + 冷启动。
4. 以上均不改变「restore 不自动绑定 archive」的既有决策。

## 8. 模型修正（2026-09-15 11:40，用户指出）

原第 1.1 / 2.2 节把 restore 当作「恢复到当前活动会话」，那是**单 agent 时代**的形态。GA-Hub 是**多会话并行**：

- 每条 hub 会话本来就有自己的绑定归档（`archive_path`），冷启动自动加载 → 「恢复自己的会话」= 在会话栏选中它，多余；
- 真正缺的能力只有一条：把**没有会话归属的归档**（飞书/微信/CLI 裸日志）变成一条会话；
- 而 copy 模式下，这件事的天然形态就是 **新建会话 + 导入上下文**（copy + 绑定），目标无需选择。

因此动作集合收敛为：

| 需求 | UI 动作 | 后端 |
|---|---|---|
| 继续已有会话 | 会话栏选中 | 已有 |
| 把飞书/微信记录变成会话 | **导入为会话** | 新建 session + copy 归档 + 绑定 |
| （可选）把会话重置回某归档 | 覆盖/重置 | 暂不做 |

**必须的 UI 区分**：历史页列的是 GA 全部归档，其中「已绑定某会话」的应给「打开该会话」，只有「未绑定」的才给「导入为会话」；否则一条记录会挂两条会话（即用户担心的管理混乱）。后端已有 `find_by_archive`，列表接口补 `bound_session_id` 即可。
