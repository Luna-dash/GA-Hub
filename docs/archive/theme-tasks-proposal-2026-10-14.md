# 主题任务：需求分析与推荐方案

状态：2026-10-14 只读源码调研后形成的建议；用户已基本认可总体方向，并补充模型设置、简洁运行态及折叠报告需求（见第8节，优先于前文通用展示建议）；仍未实施、未修改业务源码、未触发实际任务。

## 1. 需求定位

主题任务不是新 Agent、定时任务、一次性提示词模板，也不是新项目；它是把已有会话转为适合长期保留、按需调用的任务入口。

核心：一个稳定主题 + 一个原有会话 + 一条默认执行指令 + 结果优先的交互。转入后原 session_id、上下文、归档、模型与项目绑定不变，仅改变管理位置；默认不再占普通聊天会话栏。项目绑定和主题任务属性正交，自由会话、项目会话均可转入。

## 2. 已核实的现有能力

- `server/schemas.py:446-500`：HubSession 已有 id、kind、模型、归档与 project_name/path；RunSubmit 接受 text/images/source。当前没有主题任务字段及其配置接口。
- `server/services/session_metadata.py:1-5,75-138,201-219`：sidecar 保存会话标签和偏好，不保存会话消息；原子写入，现 update 使用明确字段分支，新增字段必须同步处理，不能只前端传入。
- `server/routes/sessions.py:197-208`：会话接口默认只排除 kind=system，不应把用户主题任务假扮系统通道来实现隐藏。
- `server/routes/sessions.py:314-340`：POST `/api/sessions/{session_id}/runs` 可在原会话提交新请求、返回运行身份；同会话串行与运行恢复已有守卫。
- `server/services/session_runtime_factory.py:178-235`：按归档恢复同会话（restore_wm=True），并按 project_name 激活原项目。主题任务不应绕开这条链路。异常归档已有退化处理，因此不能承诺任意损坏情况下都能完整恢复。
- `webui/src/components/SessionRail.tsx:160-166`：现按自由会话/项目分组；主题应在展示派生层筛除，不改变全局会话全集。
- `webui/src/config/navigation.ts:10-20`、`webui/src/App.tsx`：已有 `/tasks` 是定时任务；主题任务应有独立导航和路由，不能直接混进 cron/interval 模型。
- `webui/src/pages/LiveChat.tsx:92-109`：完整会话列表参与运行态与页面逻辑，隐藏仅应作用于普通栏显示集，避免深链接打开、模型解析、通知等失去目标。
- `webui/src/hooks/useDesktopNotifyEffects.ts:1-58`：已存在独立于聊天页挂载的 `session:runtime` 全局事件与完成/失败/需用户回复分类；主题页可复用，通知打开位置需适配。
- `server/schemas.py:524-564`、`server/services/archive_identity.py`：运行终态有 completed_run_id/outcome；归档消息已有 run_id/logical_id，并验证归档前缀以应对重写。历史无身份时不猜测身份。

以上是源码能力核验，不是新增主题页的端到端验收。

## 3. 产品交互

### 转入

会话菜单新增「转为主题任务」，设置名称和默认执行指令（可从用户消息显式选择并预览；不能默认把最后一句“继续”当任务定义）。确认后写入配置、不执行、不新建会话、不搬移历史、不解除项目。

还原用「移回普通会话」，不是删除会话。运行中也不因转入/移回而停止执行。

### 独立页 `/theme-tasks`

导航名「主题任务」，靠近实时聊天和定时任务。顶部搜索、状态筛选、按项目筛选。主区响应式任务卡片；多任务时可再补紧凑列表，但第一版只做一种主布局。

每卡片：名称、项目/自由任务标签、运行状态、最近运行时间、最近结果摘要与查看标记；按钮「运行」「查看结果」「调整」。运行中按钮变为「查看进度」，不重复提交。默认按固定任务顺序/置顶展示，最近运行可作为可选排序，不因每次完成让布局剧烈跳动。

点击运行留在此页，不自动跳聊天。结果展示在详情面板：本次请求、状态、最终答复、最近执行记录；执行过程默认折叠，必要时「打开完整会话」返回原聊天。

手机详情使用全屏面板；桌面用侧面板或页内详情区，避免另造一套聊天系统。

### 三种操作必须不同

1. 查看上次结果：只读取，不运行、不消耗模型调用。
2. 按默认要求运行：把保存的默认指令发给原 session_id。
3. 调整后运行：编辑本次完整请求或追加临时要求，默认只本次生效；显式勾选「保存为默认要求」才影响以后。

例：默认“检查各平台今天的签到状态，列出已签到、未签到和异常；仅检查，不代替我签到”。临时要求“本次只检查 A 平台”。用户可以把默认指令改成实际执行签到，但查看历史、检查状态、执行签到不能被 UI 偷偷混为一谈。

## 4. 架构推荐

第一版一主题任务对应一会话，不建立多会话聚合、不创建工作流引擎。

### 配置层

建议在会话 sidecar 增加独立 `theme_task` 配置：

```text
null | {
  enabled: boolean,
  title: string,
  default_prompt: string,
  pinned: boolean,
  sort_order: number
}
```

保留现有 kind 的 user/system 语义，不新增 kind=system 隐藏技巧。旧记录无字段默认为普通会话；字段须经后端 schema/store/update 与前端类型一致地读写。主题名允许与会话名独立，以免重命名主题破坏原会话标题；第一版也可默认使用会话标题减少配置。

全局 sessions 保持全集；SessionRail 展示派生集排除 enabled 的主题任务，查找会话、深链接、模型、运行态仍使用全集。主题详情临时打开完整聊天时，在主区明确标记为主题任务，不自动移回普通栏，也不把当前会话挤出可访问状态。

### 执行层

所有执行最终复用原 coordinator.submit 路径，使用原 session_id、原模型与项目，不新建系统通道。

建议增加很薄的主题任务 API：

- `PUT /api/sessions/{id}/theme-task`：设置/修改配置，转换不执行。
- `DELETE /api/sessions/{id}/theme-task`：撤销主题管理，保留会话。
- `POST /api/sessions/{id}/theme-task/runs`：按已保存默认指令或显式本次覆盖提交，传 request_id（幂等）和配置版本。

这些路由是建议，当前不存在。普通运行入口保持兼容；薄路由只负责解析配置、幂等与关联记录，不复制执行引擎。双击、前端超时后的重试必须以同一 request_id 返回同一次受理结果，不能因第一次任务已快速结束而又执行一遍；并发忙由现有后端 guard 裁决，不承诺第一版自动排队。

### 运行与结果层

配置与执行记录分开。主题执行索引记录 request_id、session_id、run_id、执行时配置版本/实际请求快照、起止时间、outcome 和查看标记；消息正文仍由 GA 原生归档提供，不复制成第二份会话历史。执行索引是可追踪触发信息，不是另一个聊天真相源。

本次结果必须依据 run_id 读取/投影，不能直接把最新 assistant 当本次结果（可能是旧结果、追问或后续另一轮）。现 messages API 有分页及 run_id 字段，但没有本轮专用结果查询；宜补 run-scoped 读取/汇总能力，避免完整历史扫描及只读末两条造成串结果。

运行事件负责提示变化，刷新/重开依靠持久配置、执行索引与运行快照重新拉取，不仅依赖一次性通知。提交成功是“已开始”，stream 结束不是任务成功，run completed 也只代表处理结束，不代表“签到成功”；业务结果仍展示真实答复。没有身份的旧结果可作为历史预览注明“历史结果”，不伪造为一次主题执行。

状态建议：未运行 / 执行中 / 需要回复 / 已完成 / 失败 / 已停止；“有新结果”单独作为查看标记。需回复沿用原 ask_user 协议，第一版可直达原会话的可交互卡片，不显示旧卡片为当前待回复。断流/休眠显示连接状态，勿冒充任务停止或再次发默认请求。

## 5. 第一版范围

必须：独立页；已有会话转入/移回；默认指令；一键运行；只查看结果；本次调整及显式保存默认；同会话上下文/模型/项目复用；运行及需回复/失败提示；本次结果与最近执行记录；刷新恢复；双击/重试防重。

暂不做：定时器、批量运行、自动重试、多个模板动作、复杂参数表单、跨会话聚合、工作流、独立Agent、自动重置上下文。后续可加“一主题多个快捷动作”，但不该拖大首版。长上下文继续采用原会话治理，不因任务化静默清空；重置/分支必须显式操作。

停止执行可以沿用现有 session_id/run_id 停止操作，但不混入移回操作。真实删除会话属于原有高影响删除流程，不放在主题卡片主要操作区。

## 6. 落地顺序与验收

1. 配置/schema/持久化及转入、移回，旧数据兼容测试。
2. 导航及独立页、普通栏过滤、完整聊天深链接与通知打开适配。
3. 同会话运行薄入口、幂等、执行索引与临时/持久编辑语义。
4. run-scoped 结果、状态与全局事件联动、最近记录及刷新恢复。
5. 真实 GA-Hub Web 验收，不用模拟预览替代原上下文/项目/执行链路；对真实有副作用任务采用明确授权或只读检查任务测试。

验收门槛：
- 转入前后 session_id、archive_path、项目与模型不变，转入本身没有执行。
- 普通栏不展示该任务；主题页可访问；原聊天 URL/历史仍可访问。
- 查看历史结果不发 POST runs；运行使用保存指令而非历史最后一句。
- 临时要求仅一次；持久修改显式保存，执行记录保留当时实际请求。
- 双击/同 request_id 重试只受理一次；同会话已有任务返回忙且不丢失正在执行的请求。
- 本轮完成、失败、取消、需回复不误分类；无最终文字时如实说明，不回退旧结论冒充本次成功。
- 切页/刷新/休眠恢复后同一 run_id 继续展示，不重复运行；通知回到主题详情。
- 移回普通会话可逆、无历史丢失；项目绑定任务与自由任务都通过。

## 7. 推荐结论

采用“会话任务化”的轻量方案：独立管理页 + 固定手动执行指令 + 结果优先详情，底层完全复用原会话。核心新增成本是配置、展示派生集、幂等触发与按本轮定位结果；不是重新建设任务调度系统。相比纯书签足够好用，相比新引擎足够克制。


## 8. 用户认可方向后的展示与模型补充（2026-10-14）

用户明确要求：模型通过设置按钮选择，卡片显示执行模型；需考虑模型改名；任务执行时不罗列过程，动画+计时+本次turn计数；过程与会话历史统一入口；完成报告可折叠。以下为细化设计建议，未实施。

### 8.1 卡片与设置

卡片常驻：名称/项目、模型标签、设置齿轮、运行状态、操作、最近一次报告。不放模型下拉框。齿轮打开轻量设置面板，含名称、默认执行要求、执行模型；保存不触发执行。模型选择沿用当前可用模型清单，显示用户配置别名与实际模型名，区分同模型不同配置。

模型单一真源采用原会话模型绑定（未来升级为模型身份引用时亦一致），不另复制到主题配置形成两个默认值。转换继承原绑定；设置通过统一会话绑定服务保存，不改变全局默认或其他会话。任务页和完整聊天内显式改模型都作用于同一个会话，需同步刷新卡片。执行中模型选择禁用，避免中途切换；显示本次启动时的实际模型快照，结束后卡片显示下次将用的当前配置，报告另标本次模型。

### 8.2 模型身份与改名

已核实：`server/services/llm_registry.py`经`frontends/gahub/bridge/model.py:model_snapshot`获取配置赋值名→index，现有llm_key为配置赋值名而非永久UUID。顺序变化可保持键绑定，但配置赋值名修改会使旧键失效；现有部分默认解析会回退第一项，主题任务不能直接沿用这一静默回退。没有读取任何密钥文件。

推荐：模型目录提供Hub管理的稳定model_ref_id（身份）+当前llm_key（运行时寻址）+可变显示别名与当前实际model_name（展示）。会话保存稳定身份，不存下拉位置/列表index，不以显示名或实际model_name为唯一键；同名模型可能有不同通道/参数。仅改显示别名不改变身份；运行时解析身份到当前llm_key，再走已有模型切换路径。每次受理执行记录当时身份、配置别名及实际model_name快照，历史报告不随改名变成另一模型。

边界：现有原始配置不暴露永久ID；若在Hub外直接修改配置赋值名，Hub无法仅凭前后名字可靠判断是重命名、删除再新增、还是替换配置。第一版可采用轻量Hub身份映射+显式重新关联（也可先保留llm_key并提示重选，但这只能失效保护，不能宣称已实现稳定身份）。外部改名/删除后无法确定映射时标记“模型待重新关联”，阻止运行；设置里用户选定新条目后才能继续。不要按列表位置、名字相似度、实际model_name自动替换；不读取/存储密钥来推断身份。若未来扩展GA原生桥或配置格式须另获修改授权。

同一配置身份下实际模型改名/替换时，卡片即时显示新model_name，后续执行跟随该配置；旧报告保留当时快照。需要严格固定实际模型版本是另一个可选需求，当前不额外引入版本锁。

### 8.3 简洁运行态及动画

推荐横向状态条：小型环形轨迹动画 + “执行中” + `01:28` + `4 turns`。约18–22px的细环单段高亮缓慢旋转（约1.6s/圈），沿现有页面配色，中心稳定小点；没有日志滚动、步骤列表、工具名称，也没有虚构百分比。环不代表进度。

- 空闲：静态图标，显示最近运行时间。
- 启动中：轻动画+“正在启动”，turn尚未产生为0，不预估完成时间。
- 执行中：连续旋转，elapsed与turn文本稳定更新，不闪烁、不随计数变化动画重启。
- 等待用户：暂停旋转，琥珀提示+“需要回复”，回复入口不能藏在深层历史中。
- 连接中断：显示“连接恢复中/状态待确认”；不能仅凭浏览器断线宣称任务停止或继续正常。
- 完成：停止动画，静态勾号；失败/取消分别错误/停止图标。业务成功由报告说明，不用执行完成图标保证签到成功。
- 支持prefers-reduced-motion，用静态状态替代旋转；动画只用于可见运行卡片。

计时口径：从后端受理本次任务起，结束冻结，刷新/切页/后台恢复不重置；统一run-level started_at/finished_at，不能拿组件挂载时间，也不能只用重试的单个stream时间。显示总耗时，包含等待；若需执行净耗时另行统计。后端记录为准，客户端每秒按时间戳计算，不靠累加定时器。

turn口径复用现有`conversationCounts.ts`：模型响应轮数，含工具续轮与模型响应重试，不是工具调用数、不是真实用户输入数。本卡只统计本次任务范围，不累计原会话全部历史；同一个turn的重复事件/重放去重，不按文本chunk递增，无数据时显示“—”而非伪造0。工具续轮由模型继续回应才增加。前端可复用现有turn投影，准确的实时和重试计数仍需后端run级去重标识/状态输出补齐，现有runtime响应本身不提供run-level计时及turn总数。

### 8.4 过程与历史的统一入口

卡片只有一个“过程与历史”入口，打开共用侧面板（移动端全屏），内部两页签：本次过程、完整会话。本次过程按run_id定位；完整会话复用现有历史/聊天展示并可继续交互。打开面板不执行任务，不改变普通会话栏的任务分类。复用已有转录/执行过程组件，不另写一套文本解析器；沿用当前原生thinking不直播的边界。

### 8.5 可折叠报告

报告不是会话历史，也不默认启动另一个模型做总结；直接展示本次最终答复，Markdown/表格/链接沿用现有渲染。标题：执行报告 + 时间 + 耗时 + turns，可展开/收起、复制；本次模型在报告信息中保留。收起后只显示标题与纯文本短预览，所有预览必须来源于本次答复，不编造摘要。

建议新完成结果自动展开（首屏限制高度，正文内部滚动），已查看后再次进入遵循折叠选择；以run_id保存状态，不每个事件强制展开。过程面板的详细内容不能因报告完成抢焦点。新任务开始时上一份报告保留但收起，清楚标“上次报告”，本次完成后替换为最新报告，旧报告从历史访问。

无最终答复、仅工具调用结束：明确“本次无文字报告”，过程仍可打开；失败/取消显示本次原因或中断说明，不包装成成功报告，不拿上一轮结论顶替本次。等待用户时给清晰问题与回复入口，不当成最终报告。

### 8.6 新增验收点

- 设置按钮内选模型，卡片无常驻下拉；刷新后选择保留，与会话绑定一致，不影响其他会话。
