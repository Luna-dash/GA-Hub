# GA-Hub 独立代码审查（2026-09-29）

## 结论与边界

审查基线：`7f25d914bfdb694ab4370ffd8f406c3ca3839e5b`。源码工作树基线干净；审查报告本身为新增未跟踪文档。本轮不修改源码、不提交、不重启生产服务。

复核后的结论是：**整体分层方向合理，常规回归基础较好；有一个确定阻断完整构建门禁的问题，另有两个文件处理策略的条件性安全/产品风险，当前均按P2记录。**不建议据此大规模重写架构。

方法参考 Google Engineering Practices 的《What to look for in a code review》（来源：`https://google.github.io/eng-practices/review/reviewer/looking-for.html`，2026-09-29查阅）：核对设计、功能、复杂度、测试有效性、注释与行为一致性；不以个人风格偏好阻断。本次是现有代码库的风险导向抽样审查，不是全仓逐行认证，也不是仅审最后一个提交。

主要检查：应用组装及生命周期、服务所有权、事件投递与会话准入、元数据持久化、聊天历史异步状态、文件预览与默认打开、桌面临时目录清理及构建门禁。Rust只做源码检查，未执行Cargo测试或真实清理；未运行完整桌面打包、浏览器利用链或生产环境端到端测试。

## 主要发现（按修复优先级）

### R1 · P2：文件预览端点缺少主动内容隔离

- 位置：`server/routes/upload.py:422-428`，核心为428行 `return FileResponse(resolved)`；对照同文件普通上传下载端点的附件/类型防护。
- 已验证：在隔离临时目录中放置无脚本HTML，通过测试客户端请求 `/api/files-by-path`，返回200，`Content-Type: text/html; charset=utf-8`，没有 `Content-Disposition: attachment` 或 CSP。路径限定只解决读哪些文件，没有解决内容在哪个安全上下文解释。
- 评级边界：这是**条件性防护缺口**，不是已证明的任意远程利用。前端当前主要将该URL用于图片资源；实际危险性取决于不可信HTML/SVG能否进入允许根目录，以及用户/桌面壳是否将该URL作为同源文档导航打开。
- 触发前提与风险推断：可影响允许目录中文件内容的一方，诱导用户在Hub服务的浏览器同源上下文打开此预览URL，可能让HTML主动内容获得Hub同源权限并调用本地接口。这不是声称任意外站无条件绕过CORS；也没有实际执行浏览器攻击链。桌面壳与浏览器模式的导航行为可能不同，需分别补测。
- 建议：默认非可信内容走附件下载；仅允许经过明确评估的被动媒体内联，对SVG等主动内容独立处理。需要HTML预览时使用独立源或严格sandbox/CSP，不能只加nosniff后仍按text/html内联。
- 验收：对HTML/SVG等主动内容增加两套文件服务端点一致性回归；浏览器同源测试确认脚本不能调用Hub API，且原有图片预览不退化。

### R2 · P2：源码扩展名白名单与系统默认打开语义不完全一致

- 位置：`server/routes/upload.py:44-46`（允许.js/.py等），`:213-240`（尤其236行Windows `os.startfile`），`:380-390`（reveal路由）。
- 已验证：隔离无害.js文件经 `/api/files/reveal` 返回200，mock记录确实调用 `os.startfile(path)`；本机只读查询得到 `.js=JSFile`、`JSFile=C:\\Windows\\System32\\WScript.exe "%1" %*`。没有执行脚本或启动关联应用。
- 评级边界：现有阻断扩展名集合已拒绝常见可直接执行类型（如`.exe`、`.vbs`、`.bat`、`.ps1`等）；但`.js`等源码仍会交给操作系统关联程序，若用户或部署环境把它们关联到解释器，打开动作可能执行内容。这是用户触发的设计风险，不是接口本身无条件远程执行。
- 影响：注释承诺源码在编辑器查看，但系统默认关联可能是解释器。用户打开代理引用或收到的源码文件时，可能以当前用户权限执行内容；风险取决于文件关联和是否触发打开。
- 建议：源码显式使用可信文本查看器或只在文件管理器定位；不要把扩展名可读等同于系统open安全。不要仅屏蔽`.js`而保留同类关联风险。
- 验收：模拟.js/.py等关联至解释器，断言源码查看路径不会调用系统默认open；文档/图片与“在文件夹中显示”分别回归。

### R3 · P2：新增桌面环境变量未登记，后端契约测试失败

- 位置：`src-tauri/src/mei_cleanup.rs:119,124`，`tests/test_env_registry.py:66-79`；完整构建影响位置 `scripts/build_all.py:393-408`。
- 已验证：`GAHUB_MEI_SWEEP_ALLOW_REAL_TEMP` 与 `GAHUB_MEI_SWEEP_DRY_RUN` 不在注册集合；全量pytest的唯一失败是 `test_every_ga_hub_name_is_registered`。独立重跑该测试文件仍为1 failed / 1 passed，排除仅由整套测试顺序造成的失败。
- 影响：`--full`在前端构建之后运行后端测试，此失败将使编排中止，不能继续sidecar和Tauri阶段。这是根据实际失败与构建调用链得出的结论；本轮没有运行真实完整构建。
- 建议：按现有环境变量注册规范登记作用域、含义和默认行为，并同步必要契约说明；不建议删掉扫描规则或靠重命名逃避登记。
- 验收：注册测试和全量pytest通过，再单独执行获准的完整构建验收。

## 三个维度的独立评价

### 结构合理性：方向合理，复杂度集中在少数运行时模块

正面证据：HTTP路由与服务层有明确依赖方向，`tests/test_import_direction.py:1-14`声明且实际测试约束services不得反向依赖routes/HTTP框架，路由共享状态交给服务所有者。应用组装根通过 `app.state.session_lifecycle` 显式绑定会话生命周期（`server/main.py:270-275`）。

改进建议（非缺陷）：`chatStore.ts` 1206行、`conductor_service.py` 1419行、`agent_service.py` 1203行、`session_coordinator.py` 1029行。规模是进一步查看职责的线索而非自动判错；生成的8117行schema与大型测试文件不计入人工业务复杂度结论。优先沿稳定职责拆出聊天历史加载/事件归并和恢复策略，不为了文件长度机械切片，也不新增通用框架。

### 代码有效性：常规回归有基础，安全语义与跨语言契约仍有缺口

独立运行前端519项测试和类型检查通过；后端1122项通过但1项确定失败。文件操作的两个问题说明“能返回200”“调用了默认应用”不等于满足安全目标。当前证据支持修复具体边界，不支持认定整个业务功能无效。

现有事件生命周期、元数据失败处理和历史请求取消/会话校验已有保护，本轮未将已存在的防护误报为缺失；也未据此证明所有竞态都已排除。

### 架构清晰性：所有权正在显式化，仍有兼容层的理解成本

`server/services/app_services.py:1-6,24-38`明确记录进程级服务所有者，便于状态和停止路径使用已经创建的实例；但文档同时明确保留兼容singleton getter。两条访问路径共存不是本轮证实的多实例故障，却增加依赖与生命周期推理成本。

建议逐步让请求依赖从app作用域取得服务实例，兼容getter限于适配层，并用双app/部分启动失败/重复关闭测试守住所有权；在有覆盖时小步迁移，不一次性重构全部服务。文件服务应收敛“读文件—判断内容—决定呈现或打开方式”的共享政策，避免不同端点各有一份安全语义。
